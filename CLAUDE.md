# pdf2dwfx — Project brief

## About the person you are working with
- The project owner is an architect, **not a programmer**. Explain everything in plain, non-technical language.
- Work in small steps. Before any big decision (new library, change of approach, restructuring), explain the options simply and ask first.
- At the end of every task, give a short plain-language summary of what changed and **exact step-by-step instructions** for how the owner can test it (which file to open, what to click, what they should see).
- The owner tests output in **Autodesk Design Review** and **DWG TrueView** on Windows. A file is only "correct" if it works there.

## What the app does
Converts vector PDF drawings (exported from CAD software) into **DWFx** files suitable for submitting architecture projects to Portuguese municipalities (câmaras municipais), whose reviewers check drawings in DWF viewers.

## Output requirements
- **Format:** DWFx (OPC/ZIP package with XPS FixedPage graphics plus DWF metadata). Classic DWF (W2D) is optional and out of scope for now.
- **Sheets:** each PDF page becomes one DWFx sheet with exactly the same paper size (an A1 PDF page becomes an A1 sheet). Drawings keep their position on the sheet.
- **Layers:** PDF Optional Content Groups (OCGs) become DWFx layers that can be switched on/off in Design Review. If a PDF has no layers, put everything on one default layer (grouping by colour is a later, optional feature).
- **Units and scale:** real-world units are always **metres**. Viewports must carry their scale so the Design Review measure tool reports correct real-world distances. Read scale from PDF measurement viewport data (/VP, /Measure) when present; otherwise the user provides the scale (e.g. 1:100), possibly several per sheet (e.g. plan 1:100, details 1:20).
- **Hatches and fills:** preserved visually as geometry (solid fills, pattern fills, line hatches). DWF has no editable hatch entity, so faithful geometry is the goal.
- **Text:** preserved and readable.
- **File size:** target at most 500 KB per sheet and 30 MB per file (Portuguese municipal limits, e.g. Maia). Avoid embedding raster images where vector is possible.
- **Digital signing:** required by several municipalities but **out of scope** until a later milestone.

## Core principles (non-negotiable)
- **Fully local.** The app never connects to the internet: no telemetry, no update checker, no automatic crash upload, no networking libraries.
- A CI test runs conversions with network access blocked; it must always pass.
- **Crash reporting is user-controlled:** on a crash, write a plain-text report to a local file and show it in a dialog with buttons: **Email report** (opens a `mailto:` draft with a short summary; the user attaches the file and sends it themselves), **Copy to clipboard**, **Open report folder**, and a link to open a GitHub issue. Reports contain only error details, app version, OS, and harmless PDF statistics (page count, page sizes, number of layers/paths) — **never drawing content, text from drawings, or file names**.

## Technology
- **Python**, managed with **uv** (install uv if missing).
- **PyMuPDF** to read PDFs (vector paths, fills, layers, text).
- Our **own DWFx writer** (zip + XML). Do not link or bundle the Autodesk DWF Toolkit. Its source (found in the OSGeo MapGuide source tree) may be read only to understand the format; do not copy its code.
- Reference DWFx files published by AutoCAD/Revit are used to check our output structure.
- **PySide6** for the graphical interface (later milestone). Keep the converter core completely separate from GUI code.
- **pytest** for tests.
- **PyInstaller** for packaging: single `.exe` (Windows), `.app` in `.dmg` (macOS), AppImage (Linux), all built by **GitHub Actions**, with SHA-256 checksums and build attestations.
- **License: AGPL-3.0** (required by PyMuPDF).

## Cross-platform rules
- Developed on Windows, but must work identically on **Windows, macOS and Linux**.
- Use `pathlib` for all paths; never hard-code `\` separators or drive letters in code.
- No OS-specific libraries or APIs.
- Add a `.gitattributes` to normalise line endings.
- From milestone 1 onward, GitHub Actions runs the tests on Windows, macOS and Linux on every push.

## Test files and privacy
- **Never commit real project drawings** to this public repository.
- Private test PDFs and reference DWFx files live **outside the repo** in `C:\Projects\pdf2dwfx-private-tests` on the owner's machine. Tests that use them must skip automatically when the folder is absent (e.g. in CI).
- Files inside the repo (`tests/fixtures`) must be synthetic, generated by scripts, or explicitly shareable.

## Milestones (do one at a time, in order)
0. Repository setup: git, `.gitignore`, `.gitattributes`, AGPL-3.0 license, README (Portuguese and English), uv project, create public GitHub repo `pdf2dwfx` with `gh`, first push.
1. Single PDF page → DWFx with all geometry, correct paper size, opens in Design Review. CI on all three OSes.
2. Layers from PDF OCGs, toggleable in Design Review.
3. Multiple pages → multiple sheets in one DWFx; readable text.
4. Scale: viewports in metres so measuring in Design Review is correct (from PDF data or user input).
5. File size optimisation to meet municipal limits.
6. Simple GUI (PySide6): choose PDF, set scales, convert.
7. Crash reporter as described above.
8. Packaging and releases via GitHub Actions (.exe, .dmg, AppImage, checksums, no-network test).
9. Later: digital signing of DWFx.
